# kino-analytics: аналитика онлайн-кинотеатра на PostgreSQL

Учебный, но приближенный к реальности проект продуктовой аналитики на чистом SQL. Здесь схема подписочного онлайн-кинотеатра, генератор правдоподобных данных за год и 12 запросов, которые отвечают на вопросы продакта: сколько людей смотрит, как они удерживаются, где теряем подписчиков, что досматривают и кого пора возвращать. В CI данные генерируются в настоящем PostgreSQL 16, проверяются 18 утверждениями и все запросы собираются в отчёт.

## Что внутри

```
schema/01_schema.sql   таблицы, ограничения, индексы
schema/02_seed.sql     генератор данных на SQL: 5000 пользователей, ~217 тыс. просмотров, ~18 тыс. оценок
queries/01..12_*.sql   аналитические запросы, у каждого в шапке вопрос и техника
tests/checks.sql       18 проверок целостности данных и правдоподобия аналитики
scripts/report.sh      выполняет все запросы и собирает отчёт в Markdown
```

**Модель данных:** пользователи с городом и устройством, тарифы (пробный, базовый 299 ₽, стандарт 499 ₽, премиум 799 ₽), подписки как непрерывные периоды, ежемесячные платежи, каталог из 400 фильмов и сериалов с жанрами, сеансы просмотра (сколько минут посмотрели) и оценки. Ограничения `CHECK` и внешние ключи не дают записать невозможное: например, оценку 11 или подписку, которая кончилась раньше начала.

## Как сделан генератор данных

Данные генерирует сам PostgreSQL, без Python и CSV-файлов:

- `setseed(0.42)` в начале скрипта делает данные воспроизводимыми: у всех получатся одни и те же цифры. Параллельные планы отключены, потому что они меняют порядок вызовов `random()`.
- Регистраций к концу года больше (`sqrt(random())`), города распределены неравномерно (`power(random(), 1.6)`).
- 58% переходят из пробной недели на платный тариф. Срок жизни подписки — геометрическое распределение с оттоком около 9% в месяц (`-ln(1 - random()) / 0.094`).
- Популярные тайтлы смотрят чаще (`power(random(), 2)`). Досматриваемость и оценки зависят от скрытого «качества» тайтла, поэтому запрос 10 находит между ними настоящую связь (corr ≈ 0.53).
- Сериалы иногда смотрят запоем: после серии идут ещё 2–5 подряд. Именно их и находит запрос 08.

Подводный камень, который здесь учтён: `random()` в некоррелированном `LATERAL`-подзапросе PostgreSQL вычисляет один раз на весь запрос, и все строки получили бы одинаковое значение. Поэтому случайные величины считаются в списке выборки, где они вычисляются для каждой строки.

## Проверки

`tests/checks.sql` падает с понятным сообщением, если что-то не так:

- **Целостность:** у каждого ровно одна пробная неделя, подписки одного человека не пересекаются (`daterange &&`), платежи только по платным подпискам, внутри их срока и на сумму тарифа, никто не смотрит до регистрации и дольше хронометража, оценку ставит только тот, кто смотрел.
- **Правдоподобие:** конверсия около 58%, отток около 9% в месяц, помесячная выручка сходится с суммой платежей, оценка и досматриваемость связаны (corr > 0.5), запойные просмотры есть в данных.
- **План запроса:** поиск просмотров пользователя за период идёт по индексу `views_user_time_idx`. Это проверяется разбором вывода `EXPLAIN`. А строки `views` лежат почти по порядку времени (корреляция в `pg_stats` > 0.9), без этого BRIN-индекс был бы бесполезен.

## Запуск

```bash
createdb kino
psql -d kino -f schema/01_schema.sql
psql -d kino -f schema/02_seed.sql        # около 3 секунд
psql -d kino -f tests/checks.sql
PGDATABASE=kino bash scripts/report.sh > REPORT.md
```

Или любой запрос по отдельности: `psql -d kino -f queries/08_binge_sessions.sql`.

## Индексы

| Индекс | Зачем |
|---|---|
| `views (user_id, started_at)` | активность пользователя за период (запросы 08, 11) |
| `views using brin (started_at)` | компактный индекс для отбора по времени: генератор вставляет сеансы по возрастанию времени, как это происходит в живой системе |
| `subscriptions (user_id) where ended_on is null` | частичный индекс только по активным подпискам (запрос 11) |
| `subscriptions (user_id, started_on)` | первая платная подписка пользователя (запрос 05) |
| `payments (paid_on)` | выручка по периодам (запросы 03, 12) |
